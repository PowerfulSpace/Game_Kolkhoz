# SPEC.md — спецификация продукта «Колхоз»

Этот документ описывает **что** такое «Колхоз» и **как** он должен 
работать с точки зрения пользователя. Технические детали — в 
`ARCHITECTURE.md`. Модель предметной области и правила — в 
`DOMAIN_MODEL.md`. Дизайн — в `DESIGN_SYSTEM.md` и `UI_SPEC.md`.

---

## 1. Проблема

Во время игры в бильярд компания из 3–8 человек ведёт счёт 
забитых шаров. Каждый забитый шар даёт одному игроку `+1`, а 
игроку, который бил до него, — `−1`.

**Как считают сейчас:**
- На бумажке — теряется, рвётся, неудобно.
- В голове — забывается, приводит к спорам.
- В заметках телефона — долго, неудобно, не приспособлено.

**Что происходит из-за этого:**
- Споры «а сколько у меня было?».
- Ошибки в счёте.
- Испорченное настроение.

---

## 2. Решение

Мобильное Android-приложение **«Колхоз»** — простой счётчик для 
бильярда.

**Ключевые свойства:**
- Работает **оффлайн**, без интернета.
- Запускается за **2 секунды**.
- Основное действие — **одно нажатие** («Забил»).
- Автоматически считает `+1` и `−1` по правилам «Колхоза».
- Хранит историю ударов и партий локально.
- Поддерживает **undo** последнего действия.

**Главный принцип:**

> **Меньше интерфейса — больше игры.**

---

## 3. Пользователь

**Целевой пользователь:**
- Компания друзей 3–8 человек.
- Играют в бильярд регулярно (раз в неделю / месяц).
- Возраст 20–50.
- Используют Android-смартфоны.
- Один из компании ведёт счёт (или все по очереди).

**Контекст использования:**
- Бильярдная, клуб, бар, гараж.
- Шумно, темно, руки заняты кием.
- Телефон лежит на столе или в руке.
- Партия длится 30–120 минут.

**Что важно пользователю:**
- Быстро нажать кнопку между ударами.
- Видеть, кто сейчас бьёт и какой счёт.
- Не спорить о цифрах.
- Не отвлекаться от игры.

## 4. Правила игры «Колхоз»

### 4.1. Игроки

- В партии **от 3 до 8 игроков**.
- Порядок игроков **фиксирован** при создании партии.
- Имя: от 1 до 32 символов.
- Имена уникальны без учёта регистра и ведущих/замыкающих пробелов.
- Порядок **циклический**: после последнего идёт первый.

### 4.2. Удар

Каждый удар делает **текущий игрок**. Результат удара:
- `POCKET` — шар забит.
- `MISS` — промах.

### 4.3. Промах (MISS)

- Счёт ни у кого не меняется.
- Текущий игрок заканчивает ход.
- Ход переходит следующему по циклу.

### 4.4. Забитый шар (POCKET)

- Забивший получает `+1`.
- Предыдущий игрок получает `−1`.
- Забивший **продолжает бить**.

### 4.5. «Предыдущий игрок»

Это игрок, который совершил последний удар **перед текущим 
событием**.

**ВАЖНО:** при серии забитых подряд одним игроком штраф получает 
тот, кто бил **до начала серии**. Все штрафы за серию идут ему.

Серия завершается **промахом** того же игрока.

**Пример:**
Саша → промах
Петя → забил (Петя +1, Саша -1)
Петя → забил (Петя +1, Саша -1)
Петя → забил (Петя +1, Саша -1)
Петя → промах (серия завершена)
Коля → забил (Коля +1, Петя -1)

text

**Итог:** Петя +2, Коля +1, Саша −3.

### 4.6. Первый удар партии

Порядок циклический, поэтому у первого игрока тоже есть 
«предыдущий». Это последний игрок в списке.

**Пример:** игроки `[Саша, Петя, Коля, Дима]`.
- Если первым забивает Саша: Саша +1, **Дима** −1.
- Если первым забивает Петя: Петя +1, **Саша** −1.

### 4.7. Отрицательный счёт

Разрешён. Игрок может уйти в минус. Никаких ограничений 
`score >= 0`.

### 4.8. Конец партии

Партия завершается **вручную**. Приложение **не определяет** 
победителя автоматически.

Пользователь нажимает «Завершить игру» → партия сохраняется → 
показывается итоговая таблица.

## 5. Состояние и история

### 5.1. Состояние игры

Приложение хранит:
- Список игроков и их порядок.
- Историю **всех** ударов (события).
- Текущий ход.
- Текущую серию.
- Статус партии (активна / завершена).

**Счёт — производное от истории событий.** Счёт не хранится как 
источник истины. Это критично для корректного undo.

### 5.2. Undo

Undo отменяет **последнее действие**:
- Удаляет последнее событие.
- Пересчитывает состояние.
- Состояние становится **точно таким**, каким было до события.

Undo работает:
- После промаха.
- После одиночного забитого шара.
- Внутри серии.
- После серии.

Undo **не реализуется** как ручное изменение счёта.

### 5.3. История

Каждый удар попадает в историю:
- Номер удара (1, 2, 3, ...).
- Игрок.
- Результат (Забил / Промах).
- Время.

История позволяет восстановить состояние игры и разобрать спорные 
ситуации.

## 6. Экраны

**5 экранов** в MVP:

1. **Главный** — новая игра / продолжить / история.
2. **Создание игры** — количество игроков (3–8), ввод имён.
3. **Игровой** — текущий игрок, счёт, ЗАБИЛ / ПРОМАХ, undo, история.
4. **История ударов** — список событий текущей партии.
5. **Итоги** — финальная таблица после завершения.

Детали — в `UI_SPEC.md`.

## 7. UX-принципы

Приложение используется **у бильярдного стола**. Отсюда:

- **Крупные элементы управления.** Палец не должен целиться.
- **Основное действие — одно нажатие.**
- **Читаемый текст.** Имя и счёт видны издалека.
- **Без переходов.** Всё важное — на игровом экране.
- **Без инструкций.** Интерфейс самоочевиден.
- **Без случайных нажатий.** Опасные действия (завершение) — 
  спрятаны.

**Главное действие:** ЗАБИЛ.
**Второе:** ПРОМАХ.
**Третье:** ОТМЕНИТЬ УДАР.

Всё остальное — вторично.

## 9. Что НЕ входит в MVP (Out of scope)

Осознанно **не делаем** в первой версии:

| Функция | Почему нет |
|---------|-----------|
| Регистрация / аккаунты | Нет сервера, нет смысла |
| Backend | Оффлайн-приложение, сервер не нужен |
| Multiplayer | Сложно, не для MVP |
| QR-коды | То же |
| Синхронизация между устройствами | То же |
| Облако | То же |
| iOS / Web | Только Android в MVP |
| Рейтинги | Нет данных, нет смысла |
| Глобальная статистика | То же |
| Аватары / фото | Не нужны у стола |
| Несколько режимов игры | Только «Колхоз», один режим |
| Реклама | Не для компании друзей |
| Звуки | Отвлекают |
| Сложные анимации | Замедляют |
| Выбор получателя штрафа вручную | Ломает простоту |

**Принцип:** если функция не помогает **быстрее нажать кнопку** — 
её не добавляем.

## 10. Обработка ошибок

Приложение должно корректно обрабатывать:

- Пустое имя игрока.
- Слишком длинное имя (более 32 символов).
- Дубликат имени.
- Менее 3 игроков.
- Более 8 игроков.
- Повреждённые локальные данные.
- Отсутствие сохранённой игры.

**Тексты ошибок — человеческие:**

❌ `ValidationException`
✅ `Введите имя игрока`

Точные тексты — в `UI_SPEC.md`.

## 11. Критерии готовности MVP

MVP готов, если:

1. Можно создать партию на 3–8 игроков.
2. Можно провести полную партию.
3. Все правила из раздела 4 работают корректно.
4. Серии работают корректно.
5. Первый удар работает корректно.
6. Промахи работают корректно.
7. Undo работает корректно.
8. История отображается корректно.
9. Партия сохраняется локально.
10. После перезапуска партия восстанавливается.
11. Unit-тесты domain проходят.
12. Android build проходит.
13. Lint проходит.
14. Приложение работает без интернета.
