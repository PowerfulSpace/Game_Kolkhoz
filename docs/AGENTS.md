# AGENTS.md — правила работы AI-агента над проектом «Колхоз»

Этот документ — контракт между заказчиком и AI-агентом, работающим 
над проектом «Колхоз». Агент обязан прочитать этот файл до начала 
любой задачи.

---

## 1. Что такое «Колхоз»

Android-приложение для подсчёта очков во время игры в бильярд.
Полная спецификация — в `docs/SPEC.md`.

Ключевой принцип продукта: **минимум интерфейса — максимум игры.**
Приложение используется у бильярдного стола, нажимается между 
ударами, не должно требовать чтения инструкций.

---

## 2. Главные правила работы

### 2.1. Не додумывать

Если задача противоречива, неполна или невыполнима — **ОСТАНОВИСЬ 
и задай вопрос**. Не додумывай правила игры, не выбирай архитектуру 
самостоятельно, не добавляй функциональность, которой нет в 
документации.

Приоритет: **лучше задать 10 вопросов, чем сделать 1 неправильно.**

### 2.2. Не улучшать без запроса

Не рефакторить код, не переименовывать сущности, не менять 
архитектуру, не добавлять «улучшения» без явного указания в задаче.
Работать строго в рамках того, что просят.

### 2.3. Один шаг — один отчёт

После выполнения задачи — отчёт по форме из раздела 7, потом 
**ждать следующей задачи**. Не переходить к следующей задаче 
самостоятельно.

### 2.4. Не трогать чужое

Если задача касается одного модуля — не трогать другие. Если нужно 
изменение вне рамок задачи — остановиться, задать вопрос.

### 2.5. Документация — источник истины

Если код и документация расходятся — **документация права**, код 
надо исправить. Если документация противоречит сама себе — 
остановиться, задать вопрос.

## 3. Архитектура проекта

Проект — многомодульный Android:
Game_Kolkhoz/
├── app/ — UI, Compose, навигация, DI-обвязка
├── domain/ — чистая бизнес-логика (Kotlin/JVM, БЕЗ Android)
├── data/ — Room, репозитории (Android Library)
└── docs/ — документация

text

### 3.1. Правила зависимостей

- `domain` **не зависит** ни от `app`, ни от `data`, ни от Android.
- `data` зависит от `domain`.
- `app` зависит от `domain` и `data`.
- Обратных зависимостей быть не может.

### 3.2. Где что живёт

| Логика | Где |
|--------|-----|
| Правила игры (счёт, серии, undo) | `domain/rules/` |
| Модели предметной области | `domain/model/` |
| Room-сущности, DAO | `data/` |
| UI-экраны, ViewModel | `app/` |
| Тема, токены дизайна | `app/ui/theme/` |

### 3.3. Что НЕЛЬЗЯ делать

- Считать очки в UI. Только в `domain`.
- Считать очки в `data`. Только в `domain`.
- Импортировать Android-классы в `domain`.
- Использовать `System.currentTimeMillis()` в `domain` — время 
  приходит параметром.
- Использовать `Random` в `domain`.

## 4. Стек

- **Kotlin** — последняя стабильная из Version Catalog.
- **Jetpack Compose** — UI.
- **Hilt** — DI.
- **Room** — локальная БД.
- **KSP** — кодогенерация.
- **Coroutines + Flow** — асинхронность (в `domain` — только 
  `GameRepository`; `GameRules` остаётся синхронным).
- **JUnit5** — основной тестовый движок. Для Room/Robolectric-тестов 
  используется JUnit4 через junit-vintage-engine (см. 6.4).

**AGP 9.0+**: плагин `org.jetbrains.kotlin.android` не применяется, 
AGP содержит встроенный Kotlin. Это не обход, а новый путь.

## 5. Стиль кода

### 5.1. Kotlin

- Immutable по умолчанию: `val` вместо `var`, `data class` вместо 
  мутабельных классов.
- Чистые функции там, где возможно.
- Sealed class для ограниченных иерархий.
- Value class для type-safe идентификаторов (`PlayerId`, `GameId`).
- Никаких `!!` без обоснования.
- Никаких исключений для бизнес-логики — только для программных 
  ошибок (нарушение инвариантов).
- Ошибки валидации пользовательского ввода — через `Result<T>` + 
  sealed `Error`.

### 5.2. Обработка ошибок в domain

- `createGame` → `Result<Game>` + sealed `GameError`.
- `applyShot`, `undoLastShot`, `finishGame` → возвращают `Game`. 
  Некорректные вызовы возвращают исходный объект без изменений, 
  поведение задокументировано в KDoc.
- `applyShot` требует `playerId == currentPlayerId`. Нарушение → 
  `IllegalArgumentException` (программная ошибка UI).
- `recompute` — никогда не падает.

### 5.3. Комментарии

- KDoc обязателен на всех публичных функциях, классах, 
  нетривиальных свойствах.
- Комментарии — на русском.
- Комментарии объясняют **почему**, а не **что**.

### 5.4. Форматирование

- 4 пробела, не табы.
- Максимальная длина строки — 100 символов.
- Trailing comma — да.
- Импорты — без wildcard.

## 6. Тесты

### 6.1. Обязательно

- Каждая новая функция в `domain` — с unit-тестами.
- Каждый баг-фикс — с регрессионным тестом.
- Тесты — осмысленные, не заглушки.

### 6.2. Где живут

- Unit-тесты domain: `domain/src/test/kotlin/`.
- UI-тесты: `app/src/androidTest/kotlin/` (когда появятся).
- Тесты — на JUnit5.

### 6.3. Правила

- Тест проверяет **поведение**, не реализацию.
- Имя теста описывает сценарий: `applyShot with wrong player throws`.
- Один тест — одна проверка (или группа связанных).
- Никаких `Thread.sleep()` — детерминированность.

### 6.4. Разделение JUnit4 / JUnit5

- Pure unit (`domain`, мапперы `data`) → **JUnit5** 
  (`org.junit.jupiter.api.Test`).
- Room DAO и `LocalGameRepository` → **JUnit4 + Robolectric** 
  (`org.junit.Test` + `@RunWith(RobolectricTestRunner::class)`): 
  `Room.inMemoryDatabaseBuilder` требует Android-контекст и SQLite, 
  что даёт только Robolectric.
- Оба движка сосуществуют в одном `useJUnitPlatform()`: JUnit4 
  запускается junit-vintage-engine.

Зависимости (`data/build.gradle.kts`): `junit-vintage`, 
`robolectric`, `androidx.test:core`, `kotlinx-coroutines-test`.

## 7. Формат отчёта после задачи

После каждой задачи агент обязан предоставить:

1. **Что сделано** — краткое описание.
2. **Дерево файлов** — какие файлы созданы/изменены.
3. **Содержимое ключевых файлов** — если задача создала новые.
4. **Результат сборки** — вывод `./gradlew <task>`.
5. **Результат тестов** — вывод `./gradlew test`, число тестов.
6. **Отклонения** — если пришлось принять решение вне промпта, 
   обосновать.
7. **Вопросы** — если что-то осталось неясным.

Если задача выполнена **не полностью** — честно сказать, что 
не сделано и почему.

Задача считается выполненной, только если:

- [ ] Код написан.
- [ ] Код компилируется (`./gradlew assembleDebug`).
- [ ] Тесты проходят (`./gradlew test`).
- [ ] Lint проходит (`./gradlew lint`).
- [ ] KDoc на публичных API.
- [ ] Нет Android-импортов в `domain`.
- [ ] Нет warning-ов (или они обоснованы).
- [ ] Документация обновлена, если задача меняет поведение.
- [ ] Отчёт по форме раздела 7 предоставлен.

## 14. Сборка и окружение

### 14.1. Агент НЕ запускает сборку

Агент **не запускает**:

- `./gradlew` (любые задачи)
- `sdkmanager`
- `adb`
- `aapt2`
- эмулятор

Причина: сборка требует:

- записи в глобальный кэш Gradle (`~/.gradle`);
- Android SDK в системной папке;
- принятия лицензий;
- скачивания платформы.

Всё это — **вне репозитория** и **на машине заказчика**. Агент 
не имеет права это трогать.

### 14.2. Сборку запускает заказчик

Заказчик (человек) запускает `./gradlew` и присылает результат 
агенту. Агент читает результат и использует в отчёте.

### 14.3. Что агент делает вместо сборки

- `git status --short`
- `git diff -- <файлы>`
- чтение кода и документов
- статический анализ (`grep`, чтение файлов)

### 14.4. Формат в отчёте

Агент пишет в отчёте:
Сборка не запускалась агентом (правило AGENTS.md §14).
Опираюсь на результат заказчика: <команда> — <результат>,
<timestamp>.

text

### 14.5. Исключение

Если в промпте явно сказано «запусти `./gradlew <task>`» — 
агент может это сделать, НО только если:

- workspace-write доступ достаточен;
- не требуется `danger-full-access`;
- не требуется трогать системные папки.

Если требуется `danger-full-access` — агент **останавливается** 
и сообщает заказчику: «Для сборки нужен доступ к `~/.gradle` и 
SDK. По правилу §14 сборку запускает заказчик.»
